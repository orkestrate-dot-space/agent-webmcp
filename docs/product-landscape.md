## 1. Product definition

**Falsifiable paragraph.** agent-webmcp is a local-first MCP engine (7 verbs: `open/list/execute/poll/close/skill/doctor`) that attaches to tabs in a browser the user already runs, enumerates whatever WebMCP verbs the live page currently registers via `document.modelContext`, and executes agent-authored JavaScript over those verbs inside a sandboxed `execute`/`poll` codemode loop — persisting nothing — plus one compiled-in per-origin site-agent verb (`ask_<site>`, v1: `ask_mintlify`) whose row in `/agents` (`origin/description/invoke{transport,endpoint,example}/proof{verified,ref}`) names a fixed per-transport engine driver (v1: `deep-link` = open site's `?assistant=` URL in a hidden tab, wait for settled panel text, close tab) rather than arbitrary code. Sources: `src/server.ts:1-5,107-191,392-400`; `src/agents.ts:1-26,50-126`; `skills/agent-webmcp/SKILL.md:1-18`; `website/app/agents/scan.ts:1-17`; `website/sites.json:1`; `SITE-AGENTS.md:7-23,46-74`.

**Falsification conditions (any one kills the thesis):** (a) no reachable browser ever yields `toolCount>0` through this engine on a contracted origin without the engine itself injecting page JS beyond CDP navigation; (b) the `ask_<site>` answer cannot be distinguished from the site's own retrieval tier (hosted MCP search / `search_docs` / `llms.txt`) on the site's own adversarial test (the repo's "poem test": agent reasons and refuses, index retrieves — `SITE-AGENTS.md:85-101`); (c) every contracted row's `proof.verified` date goes stale on first markup/API drift and no re-verification fires before serving.

**What it is explicitly NOT (in-repo constraints):**

1. **No hosted runs.** `mcp serve` over stdio with no flags; `doctor` only reports reachability. No cloud browser, no proxy, no session store. Sources: `src/main.ts:1-53`; `src/server.ts:371-390`; `README.md:52-55` ("Two entries, same verbs… Attach locally").
2. **No stored tools.** "The engine never launches a browser… It keeps no tools: what the page serves now is the whole catalog." "Nothing is read from or written to disk for this — the row is data, the driver is engine code." "verbs resolve live-only." Sources: `README.md:34-37`; `src/server.ts:116-118`; `CHANGELOG.md:7-49` (registry/admission deletion, "Old registry files on disk are inert (never read)").
3. **No auth-walled scraping / no bypass.** "No scraping around auth/captcha/login walls. Parked, never bypassed." Transport ladder parks reasoning-API-behind-key and undocumented panel backend (`POST leaves.mintlify.com…` requiring browser-minted invisible-captcha token; verdict: "Bot-gated by design. DO NOT work around it: no token harvesting, no fingerprint spoofing"). Sources: `SITE-AGENTS.md:26-37,46-74`.
4. **No arbitrary code admission.** "A row can only pick a transport the engine already knows how to drive. No arbitrary bodies are ever admitted." `TRANSPORTS = ["deep-link","mcp","webmcp","api","dom"]` is the closed set; v1 serves one contract (`mintlify.com`, `deep-link`). Sources: `src/agents.ts:1-25`; `website/app/agents/scan.ts:5-6`; `SITE-AGENTS.md:13-23`.
5. **No second site, no listing without sign-off.** "v1 scope: mintlify complete first. No second site until signed off." "Row proof: USER SIGN-OFF ONLY… (Status 2026-10-31: mintlify row is live WITHOUT sign-off — flagged.)" Source: `SITE-AGENTS.md:26-35`.
6. **Consumer is any harness, engine changes gated.** "Consumer: any harness via the engine (not my-harness-only)." "Engine surgery: ASK EACH TIME engine code would change." Source: `SITE-AGENTS.md:26-35`.
7. **Key material hygiene.** "Key material: env only, per-command export, unset after. Never in repo." "The engine never stores credentials: auth lives in the browser profile or the driver's vault." Sources: `SITE-AGENTS.md:103-110`; `SECURITY.md:12-20`.

## 2. Innovation audit

### (a) Consume-native-instead-of-rebuild

**Claim shape:** where a site already ships an agent surface, drive that surface instead of re-implementing extraction or per-task browser reasoning.

**Closest prior art:**
- WebMCP spec itself frames pages as "Model Context Protocol servers that implement tools in client-side script instead of on the backend" — i.e., consume-don't-rebuild is the spec's premise. Source: https://webmachinelearning.github.io/webmcp/ §1 Introduction.
- Chrome's WebMCP docs frame the same contrast: "Instead of an agent reviewing the element… the website declares the element's purpose, so it's used as intended. This is more reliable than actuation." Source: https://developer.chrome.com/docs/ai/webmcp (Why WebMCP?; fetched 2026-10-31).
- Cloudflare's Commerce.com write-up makes the identical pitch for shopping: agent calls `search_products`/`add_to_cart` instead of "hunting for buttons… guess which button does what." Source: https://blog.cloudflare.com/webmcp-commerce/ (2026-10-21).
- Kapa's hosted MCP and Mintlify's Search MCP both sell "don't scrape our docs; call our retrieval" — same idea, server-side. Sources: https://docs.kapa.ai/integrations/mcp/overview; https://www.mintlify.com/docs/ai/model-context-protocol (via https://mintlify.com/docs/ai/skillmd link graph; Search MCP description in fetch 2026-10-31).

**Judgment: already done as a principle; new only in where it is applied.** The consume-native move is the WebMCP program itself and the docs-platform MCP program. What is not yet standard is consuming the *reasoning* tier (assistant answer with citations + refusal behavior) rather than the *retrieval* tier (search/read/llms.txt). The repo learned this distinction the hard way ("The poem test killed it: the agent reasons and refuses; the index retrieves. Never conflate again." — `SITE-AGENTS.md:85-101`). Nobody else documents that split as a transport ladder (reasoning-API > browser-held reasoning > retrieval > embed-API > panel-backend-probed-and-parked — `SITE-AGENTS.md:46-74`). The ladder is the novelty, not the slogan.

### (b) Per-site single-tool subagent shape with verified proof per row

**Claim shape:** one tool per site (`ask_<site>({question}) → worked answer`), row carries invoke contract + proof, user sign-off required before listing.

**Closest prior art:**
- Kapa hosted MCP exposes a single semantic search tool per project (`search_<PRODUCT>_knowledge_sources` / `search__knowledge_sources`) with rate limits and server instructions — one-tool-per-knowledge-base, but it is *retrieval*, not the site's assistant, and proof is vendor SLA, not per-row live verification. Source: https://docs.kapa.ai/integrations/mcp/overview (Tools; Rate limits: 300 req/day public OAuth, 60/min per team).
- Mintlify Search MCP: "Connect AI tools like Claude, Cursor, and ChatGPT to your hosted search MCP server so they can search and retrieve content" — again retrieval-tier, one server per docs site. Source: https://mintlify.com/docs/ai/skillmd (Search MCP card text, fetched 2026-10-31).
- Browser Use WebMCP directory lists 13,352 sites / 45,763 tools with per-site tool names and a stated methodology (loaded 322,714 pages, re-check 400 listings Oct 24 2026, 79.3% re-registered via shipped API), but rows are *observations*, not *invoke contracts* — no endpoint, no example call, no sign-off gate. Source: https://browser-use.com/webmcp (header stats + "How we found them").
- webmcp.com ("8,540 verified sites, 2.3M+ Shopify sites"), webmcpdirectory / OneScales directory (120–145 sites), and Ora audit (per-site scores) are directories/audits, not callable contracts. Sources: https://webmcp.com/?category=Commerce; https://webmcpdirectory.onescales.com/ (120 sites / 319 tools); https://browser-use.com/webmcp (platforms table: Shopify 5,190; Mintlify 203; Cloudflare 258).
- MCP registries (official `registry.modelcontextprotocol.io`; PulseMCP 20,000+ servers; Glama snapshot 23,968 servers May 2026) index *server packages*, not *site rows with live proof*. Sources: https://modelcontextprotocol.io/ (ecosystem); https://www.pulsemcp.com/api; https://clawnewbie.com/tools/glama (May-2026 snapshot caveat).

**Judgment: new combination.** Single-tool-per-site exists (Kapa, Mintlify Search MCP). Per-row live proof exists (Browser Use methodology, Ora scores). The combination — one *reasoning* tool per site + machine-readable invoke contract + dated live proof + explicit sign-off gate — has no named prior. It is also the most fragile part (see §6): proof rots on markup drift, and the current mintlify row is itself flagged as live-without-sign-off (`SITE-AGENTS.md:26-35`; `website/sites.json:1` verified 2026-10-31).

### (c) Live-only verbs, nothing persisted

**Claim shape:** the catalog is whatever the page registers right now; sessions hold handles, not tools; background runs stream back via `poll`.

**Closest prior art:**
- The WebMCP spec's lifecycle *is* live-only: registration via `registerTool`, discovery via `getTools`, unregistration by aborting the register-time signal; no persistence layer in the API. Source: https://webmachinelearning.github.io/webmcp/ §§4.2, 3 (unregister-a-tool note).
- agent-browser (Vercel Labs) already ships the CDP-hosted equivalent: daemon subscribes to CDP WebMCP events once per page session, bounded 1s initial subscribe, `webmcp list/invoke/result/cancel`, bounded summaries, `untrusted:true` on metadata. The repo's own host research documents this migration (page-JS era → native CDP era, 0.36.0–0.38.0) as the pattern to copy. Source: `docs/webmcp-host-research.md:509-532`; https://agent-browser.dev/webmcp (cited therein).
- Cloudflare Agents SDK / Durable Objects is the *opposite* bet: durable identity, local SQL storage, recoverable execution — persistence as the primitive. Source: https://developers.cloudflare.com/agents (Agent class, state, sessions, fibers); https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects.

**Judgment: already done (by the spec and by agent-browser); the repo's contribution is refusal, not invention.** Live-only is what the platform gives you for free. The repo's distinct move is deleting its own registry/admission/persistence machinery to stay live-only (`CHANGELOG.md:38-49`), which is a maintenance posture, not a moat. Durable-agents vendors win any workload that needs memory; live-only wins only where freshness and no-custody matter.

### (d) Subagent-shaped invocation for any harness

**Claim shape:** a listed origin behaves like `invoke(input) → reasoning → response` from any MCP harness's perspective, via fixed engine drivers.

**Closest prior art:**
- MCP itself is the harness-agnostic layer: "Build once and integrate everywhere" across Claude, ChatGPT, VS Code, Cursor (source: https://modelcontextprotocol.io/ — Broad ecosystem support, fetched 2026-10-31). OpenAI Apps SDK builds on MCP (source: https://openai.com/index/introducing-apps-in-chatgpt); Anthropic connectors directory lists 950+ MCP servers (source: https://claude.com/resources/articles/bringing-mcp-2026-07-28-to-claude, 2026-07-28).
- Cloudflare Agents SDK `MCPAgent` + `Agents SDK v0.6.0 changelog` (agent connects to McpAgent in same Worker through Durable Object binding) and MCP Apps / Tasks extensions (MCP 2026-07-28 spec: stateless core, Apps, Tasks) are the vendor path to "any harness, rich invocation." Sources: https://developers.cloudflare.com/agents; https://blog.cloudflare.com/mcp-v2 (stateless; "MCP servers can now run in just a Worker"); https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate.
- Inkeep's agent builder explicitly targets "Talk to Agents via A2A, MCP, and Vercel AI SDK formats" (source: https://docs.inkeep.com/pricing — Core Framework table). Kapa's Retrieval API + hosted MCP serve the same retrieval to any client (source: https://docs.kapa.ai/integrations/mcp/overview).

**Judgment: new combination at best, and currently the thinnest claim.** Harness-agnostic invocation is MCP's whole pitch; every vendor above does it for *retrieval*. The repo's variant (harness-agnostic invocation of a *third-party site's reasoning agent* through a fixed driver) is undocumented elsewhere — but v1 proves exactly one transport on one site, and the engine change gate ("ASK EACH TIME engine code would change" — `SITE-AGENTS.md:26-35`) means each new transport is bespoke engine work, not a general harness story yet.

**A note on "Jev-style" in the brief:** Jev (TypeSafe AI, launched 2026-09-15, $40M seed led by DCVC) is a *decision* model returning typed Choice/Score/Noul answers with probabilities — for routing, triage, guardrails — not a browser agent. Sources: https://openrouter.ai/blog/insights/what-is-jev; https://langfuse.com/blog/2026-09-18-using-typesafes-jev-for-evals; https://vercel.com/kb/guide/typesafe-jev-and-ai-sdk. There is no "Jev-style browser agent." If the brief meant "judgment-call" tooling, say so; otherwise drop Jev from the browser-agent set to avoid a category error.

**A note on "TinyFish":** in this environment TinyFish is a search/fetch toolkit, not browser infrastructure. No primary source was found for a "TinyFish browser infra" company comparable to Browserbase/Steel. Treat the brief's "TinyFish/Browserbase/Steel-style" as Browserbase/Steel (+ Browser Use cloud) unless a citation surfaces. Steel and Browserbase primaries are in §3.

**Where they win:** distribution and trust signals (verified namespaces, security scans, download counts, reviews). If the official registry adds "site agent" metadata, this product's contract store becomes a feature of theirs.

### Cloudflare Agents SDK / Durable Objects

Agents SDK runtime (Agent class, state, sessions, routing, WebSockets, scheduling, fibers) + tools (browser automation, sandboxed code, AI Search, MCP, payments) + deploy-once global scaling; Durable Objects = stateful addressable actors with SQLite storage, alarms, hibernation-aware billing. Sources: https://developers.cloudflare.com/agents; https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects; https://www.cloudflare.com/connect/2026/session/building-durable-agents-with-durable-objects.

**Difference:** Cloudflare bets on *durable hosted agents*; this repo bets on *stateless local invocation of others' agents*. They are complements today (this engine could run *on* Cloudflare edge; contracts could live in DO SQL), competitors tomorrow if Cloudflare ships a "site agent directory" on its WebMCP edge bridge (already injects WebMCP site-wide: https://blog.cloudflare.com/webmcp-commerce/).

**Relationship:** these vendors *are the supply*. Every site running Mintlify/Kapa/Inkeep already ships the reasoning tier this product wants to invoke. The product's job is to be the demand-side adapter they never built (cross-site, harness-agnostic, proof-carrying). Risk: any of them can expose a first-party `ask_<their-customers>` MCP and disintermediate per-site deep-links — Mintlify already ships Search MCP per site; the step to Assistant-as-MCP per site is small.

## 4. Why now (each grounded in a dated source)

1. **Agents need live web knowledge and stop at static training data.** MCP exists because "frontier models produce better, more relevant responses" when connected to live sources (Anthropic MCP launch narrative, 2024; current hub https://modelcontextprotocol.io/). Exa/Firecrawl agent endpoints (Agent runs from $0.012, mid-2026 repricings) monetize exactly this gap. Sources: https://www.anthropic.com/news/model-context-protocol; https://keirolabs.cloud/blog/exa-ai-api-pricing-2026 (2026-07-14 Agent recut).
2. **Sites already ship assistants worth invoking.** Mintlify Assistant/Agent on Pro ($450/mo, 25 credits/answer, Sep 2026 credit schedule); Kapa (200+ companies incl. OpenAI/Nokia/Docker — vendor claim); Inkeep (Postman/Anthropic/Midjourney logos — vendor claim). Dated price/schedule evidence: https://www.mintlify.com/pricing; https://documentation.ai/blog/mintlify-pricing (2026-09-17); https://www.kapa.ai/library/best-ai-documentation-search-tools-for-2026; https://www.getmacha.com/blog/inkeep-complete-guide.
3. **Sites already ship machine surfaces alongside the assistant.** Mintlify Search MCP + `llms.txt` + `skill.md` generation (up to 24h) per docs site (https://mintlify.com/docs/ai/skillmd); Kapa hosted MCP single-search-tool (https://docs.kapa.ai/integrations/mcp/overview); GitBook/ReadMe/Cloudflare MCP equivalents (secondary roundups). The retrieval tier is table stakes; the reasoning tier is the unexploited remainder — the repo's exact wedge.
4. **MCP is the distribution rail.** Claude connectors directory (950+ servers, MCP Apps, 2026-07-28 rollout: https://claude.com/resources/articles/bringing-mcp-2026-07-28-to-claude); ChatGPT Apps SDK on MCP, open source, preview (https://openai.com/index/introducing-apps-in-chatgpt, DevDay 2025); official Registry preview Sep 2025 (https://www.openhelm.ai/blog/mcp-registry-directory-guide). One protocol reaches every harness — if the row is a valid MCP tool.
5. **WebMCP standardizes the in-page verb layer.** Draft Community Group Report (editors: Microsoft + Google; *not* a W3C Standard nor on Standards Track), `document.modelContext` with `registerTool/getTools/executeTool`, `tools` Permissions Policy default `self`, origin trial Chrome 149–156, local flag `chrome://flags/#enable-webmcp-testing`. Sources: https://webmachinelearning.github.io/webmcp/ (v2026-10-27); https://developer.chrome.com/docs/ai/webmcp (May 18 / Oct 7 2026); https://chromestatus.com/feature/5117755740913664 (via Chrome docs). Supply shock dated Aug–Oct 2026: Shopify WebMCP on every Liquid storefront Aug 5 2026 + checkout Sep 28 2026 (https://shopify.dev/changelog/posts/webmcp-liquid-hydrogen; https://techcrunch.com/2026/09/28/shopify-opens-checkout-to-browser-based-ai-agents); Cloudflare edge WebMCP bridge beta + Commerce.com ~100k domains Oct 21 2026 (https://blog.cloudflare.com/webmcp-commerce/). Census: Browser Use scan finished Oct 19 2026 — 13,352 sites / 45,763 tools (https://browser-use.com/webmcp).
6. **Demand concentrates in one browser agent while supply explodes.** "Millions of pages gained tool surfaces in a week, while the population of agents able to call them stayed near one [Gemini in Chrome]" — secondary synthesis, but the underlying asymmetry (Chrome origin trial vs Firefox/Safari no signal; Edge trial 150) is primary (https://developer.chrome.com/docs/ai/webmcp; https://github.com/webmachinelearning/webmcp/blob/main/implementation-status.md). A harness-agnostic consume layer is valuable exactly in that gap.

## 5. Moat candidates (examined skeptically)

1. **Verified-working invocations + proof per row.** *Claim:* presence = invocable, with dated proof and sign-off. *Skepticism:* proof rots. Browser Use's own re-check found only 79.3% of listings re-registered via the shipped API (317/400, Oct 24 2026 — https://browser-use.com/webmcp). The repo's single row already exhibits drift risk (assistant panel selectors, viewport-dependent mounting, `?assistant=` behavior) and is flagged live-without-sign-off (`SITE-AGENTS.md:85-101`; `website/sites.json:1`). Defensibility: low unless re-verification is automated and continuous — currently a manual discipline ("Prove live before claiming. Tracebacks over memory." — `SITE-AGENTS.md:103-110`), not a system. Easily copied by anyone with a browser fleet (Browser Use, Firecrawl, Steel all have one).
2. **Local-first connect-only (no proxy, no credentials).** *Claim:* nothing to breach, nothing to host. *Skepticism:* true and cheap to copy — it's the absence of infrastructure. It wins trust and loses every workload needing persistence, scheduling, or behind-login access (Pomerado/Rindler's entire market). Durable Objects + MCP tunnels (https://platform.claude.com/docs/en/agents-and-tools/mcp-tunnels/overview) show the industry moving *toward* managed private access, not away. Moat value: negative cost (no burn), not positive lock-in.
3. **The contract registry as data.** *Claim:* rows (transport + endpoint + example) compound. *Skepticism:* one row is not a registry; the worker is "presence store" and `sites.json` the contract store with the worker source absent from the checkout (`SITE-AGENTS.md:75-84`). Data moats need scale + freshness + exclusivity; this has none yet, and the supply census (Browser Use) is public and 13,352× larger. Copy cost: one engineer, one browser fleet, one month.
4. **Distribution via any MCP harness.** *Claim:* any harness speaking the verbs can consume rows. *Skepticism:* true of every MCP server by definition (https://modelcontextprotocol.io/). The repo's harness surface is 7 verbs with prompt-cache-stable `list` ordering (`src/server.ts:242-264`) — good hygiene, not distribution. Real distribution is directory placement (Claude connectors, ChatGPT Apps, Glama/PulseMCP) plus docs-platform partnerships (Mintlify/Kapa/Inkeep as supply). None secured.

**Net:** no moat today. The only candidate that could become one is *proof freshness at scale* (continuous re-verification with public dated evidence per row) — expensive, unglamorous, and exactly what no directory currently sells.

## 6. Top risks

1. **Bot defenses and ToS (first-hand evidence on mintlify.com).** The repo probed the undocumented panel backend and hit all three: invisible-captcha token required (`captcha_required` / 420 without), fingerprint/datacenter-egress gating ("unavailable from your network"), trust-token dynamics — verdict: "Bot-gated by design. DO NOT work around it" (`SITE-AGENTS.md:60-74`). This generalizes: Cloudflare Turnstile, PerimeterX press-and-hold, and image CAPTCHAs are Steel/Browser Use product features precisely because they block this path (https://steel.dev; https://browser-use.com/stealth-browsers). The v1 `deep-link` transport survives only because it drives a *real user browser session* the way a human would — any headless/datacenter execution re-enters the bot wall (Chrome docs note WebMCP is "primarily designed for local browser workflows with a human in the loop" — https://developer.chrome.com/docs/ai/webmcp, Limitations). ToS risk is unpriced: driving an assistant UI at machine scale may violate site terms even when technically possible.
2. **Markup/API drift breaks admitted tools.** Panel selectors (`INPUT.chat-assistant-input,[role=dialog],[role=complementary]`), settled-text heuristics (200-char stability), viewport-dependent mounting (narrow unmounts the panel entirely) are all documented failure modes (`src/agents.ts:80-126`; `SITE-AGENTS.md:85-101`). No automated re-probe exists; the row carries a static `verified` date (`website/sites.json:1`). Every site redesign is a silent breakage.
3. **Dependence on no-permission interaction norms.** The product assumes sites tolerate machine-driven use of human surfaces. No primary source grants that permission generally; Mintlify meters answers (25 credits) and reserves customization/external sources for Enterprise (https://www.mintlify.com/pricing). At scale, "consume the assistant" looks like cost-shifting (reader's agent burns the site owner's credits) — expect rate limits, assistant-specific bot rules, or key requirements.
4. **Platform risk: Chrome WebMCP evolution.** The spec is a Community Group draft, not a standard; the API already renamed (`window.agent` → `navigator.modelContext` → `document.modelContext`, deprecated in Chromium 150); the declarative form path was removed Oct 8 2026 (issue #338); cross-origin `exposedTo`/`fromOrigins` landed Oct 27 2026; security/privacy sections catalog tool-poisoning, output-injection, over-parameterization, same-origin violations as open risks with mitigations "marked as approaches." Sources: https://webmachinelearning.github.io/webmcp/ (§§6.3–6.4, Status); https://developer.chrome.com/docs/ai/webmcp (under active discussion). Building fixed drivers against a moving draft guarantees maintenance.
5. **MCP spec churn.** 2026-07-28 is wire-incompatible (stateless, new headers, deprecations with 12-month window). Sources: https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate; https://stacktr.ee/blog/mcp-2026-spec-changes. Any pinned SDK or gateway assumption rots yearly.
6. **Incumbents absorb the job.** Kapa/Mintlify/Inkeep can ship first-party Assistant-as-MCP per customer (the step from Search-MCP to Assistant-MCP is trivial for them); OpenAI/Anthropic can list those servers natively; Cloudflare can inject site tools at the edge for every customer domain (already doing it for WebMCP: https://blog.cloudflare.com/webmcp-commerce/); Shopify proves platforms flip entire fleets in one changelog (Aug 5 / Sep 28 2026). Each absorption removes one row's reason to exist. The defense — being the *cross-vendor, proof-carrying* layer — only matters if vendors stay fragmented.

## 7. Open questions primary sources could not answer

1. What are the exact ToS/rate-limit terms for machine-driven use of Mintlify's `?assistant=` panel (as distinct from the metered Assistant API)? No public page states them; the pricing page meters only API answers.
2. Does Mintlify intend to expose the Assistant (reasoning tier) as a first-party MCP, and on what plan? Search MCP exists; Assistant-as-MCP does not appear in primary docs fetched.
3. What share of the 13,352 Browser Use-listed sites hold an *assistant* (reasoning tier) vs retrieval-only tools? The directory records tool names, not reasoning behavior; the poem-test split has no census.
4. What is the re-verification half-life of a deep-link row (days to breakage after site deploy)? No longitudinal data exists; the repo has n=1.
5. Which harness harms least: does `execute`-as-codemode survive MCP sampling deprecation and stateless-proxy header routing (`Mcp-Method`/`Mcp-Name`) without change? Spec SEPs describe infra behavior, not codemode ergonomics.
6. Is there a lawful, keyless path to a site's *reasoning* API distinct from driving its UI? The repo's ladder says no for mintlify (key-parked API vs bot-gated panel backend); generality unproven.
7. Who owns proof liability when a row's answer is wrong — the site, the row publisher, or the calling harness? No registry, directory, or spec assigns it.

---

## 8. Verdict

**If it wins, it is this:** every site already paid to train, ground, and serve its own answering agent, and every one of those agents is stranded behind a human-shaped widget — while every AI harness already speaks one protocol (MCP) and every user already runs one trusted browser. The product that wins is the thinnest possible bridge between those two installed bases: no new models, no hosted fleet, no credential vault, just a proof-carrying row per site (`ask_<site>` = the site's own reasoning, invoked the way its own frontend invokes it, re-verified live, dated in public) composed through whatever verbs the page natively serves. It wins on freshness and custody — the two things hosted minters and durable-agent clouds structurally cannot offer — and it compounds only if the proof ledger stays honest faster than sites drift.

**What would prove it wrong:** (a) the second and third rows cost as much as the first (each site needs bespoke panel-driving and breaks quarterly — no ladder generalizes); (b) the supply vendors expose Assistant-as-MCP natively and get listed in Claude/ChatGPT connectors, collapsing the deep-link's only advantage (keyless reasoning) to zero; (c) bot/ToS enforcement or per-agent rate limits make UI-driven invocation unreliable or unlawful outside a human-attended tab, confining the product to demos; (d) a re-verification census shows median row half-life under 30 days with manual re-proof — in which case the registry is a liability ledger, not a moat. Any one of these reduces /agents to a bookmark list; all four together end it.
